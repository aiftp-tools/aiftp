## Step 1 — サイト台帳に登録（F1 / P3）

- [ ] gwco プロジェクトの作業ディレクトリで登録:
  ```bash
  aiftp sites add --name gwco --label glocalworks.co.jp --default-profile production
  ```
- [ ] 2サイト目を登録（そのディレクトリで、または `aiftp sites add <path> --name ...`）
- [ ] 一覧確認: `aiftp sites list`（2サイト表示・**host/user/password が出ないこと**を目視）
- [ ] 機械可読も確認: `aiftp sites list --json`（**table でなく JSON** が返ること。v0.12 で修正した挙動）
- [ ] **痛点 P3 判定**: 台帳が「どのサイトがどこにあるか」を一覧化して資格情報管理の見通しが良くなったか？ → メモ

## Step 2 — `init --from` で設定継承（F2 / P1）

> 2サイト目を「gwco の設定を継承して」初期化する体験を確認。**新規テスト用ディレクトリで実施**（既存 config を壊さない）。

- [ ] テスト用の空ディレクトリを作り、そこで:
  ```bash
  aiftp init --from gwco
  ```
- [ ] 継承されること: port / protocol / FTPS mode / passive mode / server kind / ファイル名エンコーディング
- [ ] **継承されないこと（再入力を求められる）**: host / user / keychain_service / password
  - [ ] → **gwco の host/user が勝手に入っていないこと**を必ず確認（別サイトの資格情報汚染がないこと）
- [ ] 生成された `.aiftp.toml` を目視（継承項目が入り、host/user は新規値）
- [ ] **痛点 P1 判定**: ゼロから全項目 init するより手間が減ったか？ → メモ

---

## Step 3 — 宛先バナー（F3 / P2）

- [ ] gwco ディレクトリで dry-run: `aiftp push --dry-run`
  - [ ] 先頭に `⛳ 宛先: gwco (glocalworks.co.jp)` が表示されること
  - [ ] **host 等の資格情報がバナーに出ていないこと**
- [ ] 2サイト目ディレクトリで dry-run → バナーが**そのサイト名**を指すこと
- [ ] 台帳未登録のディレクトリで dry-run → `⛳ 宛先: <profile名>`（fallback）になること
- [ ] rollback も dry-run で宛先バナーが出ること: `aiftp rollback --dry-run`（該当スナップショットがある場合）
- [ ] **痛点 P2 判定**: 「今どのサイトに上げようとしているか」が一目で分かり不安が減ったか？ → メモ

---

## Step 4 — MCP `expected_site` fail-closed（F3 / P2、AI クライアント経由）

> Claude Code / Cursor など MCP クライアントから確認。AI に「gwco へ push」と指示する想定。

- [ ] MCP 設定でローカル CLI を接続（`docs/mcp.md` 参照。`command: aiftp` or `node .../dist/bin.js`、`cwd` を対象プロジェクトに）
- [ ] AI から `aiftp_push_prepare` を **正しい `expected_site="gwco"`** で呼ぶ → prepare が通ること
- [ ] **わざと違う `expected_site`**（例 存在しない名 or 別サイト）で呼ぶ → `site-mismatch` で**拒否**され、実 push が起動しない・`plan_id` が返らないこと
- [ ] 台帳未登録の cwd で `expected_site` 指定 → 同様に拒否されること
- [ ] **痛点 P2 判定（AI 運用時）**: AI が宛先を取り違えても構造的に止まるか？ → メモ

## Step 5 — keychain 命名の衝突回避（F4 / P3）

- [ ] 各サイトの `.aiftp.toml` の `keychain_service` が `aiftp:<site>-<profile>`（例 `aiftp:gwco-production`）になっているか確認
  - ※ 既存 gwco が旧命名（`aiftp:production` 等）の場合は**そのまま動く**（migration 不要）。新規 init 時のみ新命名が既定
- [ ] `aiftp sites doctor` を実行（`--connect` なしで設定検査）
  - [ ] 2サイトが同じ `default_profile` で**サイト非固有な keychain 名**を共有している場合、`keychain-collision` warn が出ること（該当する構成を作れれば）
- [ ] **痛点 P3 判定**: 複数サイトで同じ profile 名でも資格情報が衝突しない安心感があるか？ → メモ

## Step 6 — 実プッシュ（テスト用サブディレクトリ限定）

- [ ] gwco の `.aiftp.toml` の `remote_root` を**テスト用サブディレクトリ**（例 `/public_html/aiftp-test/`）に一時的に向ける、またはテスト専用 profile を用意
- [ ] `aiftp doctor`（or `sites doctor --connect`）で接続健全性を確認

- [ ] 後片付け: テストサブディレクトリのファイルを削除、`remote_root` を元に戻す

### MEDIUM-1: MCP destination payloads expose `remote_root` despite the MCP REDACTED forbidden-field contract

- Files:

- Evidence:
  - `DestinationSummary` includes `remote_root` as a typed field at `packages/mcp/src/index.ts:1286` and `packages/mcp/src/index.ts:1290`.
  - `resolveDestination()` maps `profile.remote_root` into the MCP-visible destination object at `packages/mcp/src/index.ts:1317` and `packages/mcp/src/index.ts:1322`.
  - `aiftp_push_prepare` returns that destination and also returns `expected_remote_root` at `packages/mcp/src/index.ts:919` and `packages/mcp/src/index.ts:928`.
  - `aiftp_rollback_prepare` returns both `destination` and a top-level `remote_root` at `packages/mcp/src/index.ts:2181` and `packages/mcp/src/index.ts:2192`.
- Impact:
  - This does not leak password, user, host, keychain service, or plan secret material.
  - It does violate the Task 13 MCP REDACTED review contract, which lists `remote_root` among forbidden fields. On shared hosting, `remote_root` can reveal deployment layout, tenant/domain hints, or hosting account structure to MCP clients.
- Reproduction:

- Recommended fix:
  - Remove `remote_root` from `DestinationSummary`.
  - If confirm-time binding still needs the value, keep it only inside the opaque in-memory plan and `diff_hash`, not in MCP response JSON.
  - Add regression tests that serialize `aiftp_push_prepare`, `aiftp_rollback_prepare`, and destination summaries and assert absence of `remote_root`, alongside the existing host/user/keychain redaction assertions.

  - `packages/cli/src/init-flow.ts:126`
- Evidence:
  - The registry schemas are `.strict()`, so extra pointer fields such as `host`, `user`, `password`, `remote_root`, and `keychain_service` are structurally rejected.
  - However, `name` and `path` only require non-empty strings at `packages/core/src/sites/registry.ts:11` and `packages/core/src/sites/registry.ts:14`; there is no control-character, path-separator, absolute-path, or normalization requirement.
  - CLI `sites add` writes an absolute path via `resolve(deps.cwd, path ?? '.')` at `packages/cli/src/sites-command.ts:137` through `packages/cli/src/sites-command.ts:140`, but hand-edited `sites.toml` entries are accepted by `fromRegistryDocument()` without equivalent normalization at `packages/core/src/sites/registry.ts:115` through `packages/core/src/sites/registry.ts:116`.
  - `init --from` resolves a registered site name before considering filesystem paths at `packages/cli/src/init-flow.ts:120` through `packages/cli/src/init-flow.ts:126`. A hand-edited site named like a path reference can therefore shadow the operator's intended path-style `--from` argument.
- Impact:
  - This is not a direct credential leak because F2 avoids inheriting host/user/password/keychain service.
  - A poisoned local registry can still redirect `init --from` inheritance to a different config and inherit safety/non-secret sections such as `safety`, `backup`, `connection`, `encoding`, and `quirks`.
  - Dirty names can also flow into CLI/MCP display and error strings.
- Reproduction:
  - Hand-edit `~/.aiftp/sites.toml` to include a site whose key is a path-shaped string and whose `path` points elsewhere.
  - Run `aiftp init --from <same path-shaped string>`.
  - The registry name match wins before filesystem path resolution.
- Recommended fix:
  - Add a site-name allowlist, for example `^[A-Za-z0-9._-]+$`, and reject control characters, `:`, `/`, `\`, and path-like names.
  - Require registry `path` values to be absolute normalized paths on read as well as write, or normalize and compare from a known base.
  - Add tests for malicious names like `../prod`, `client/a`, `gw:co`, and control characters.

### LOW-2: TOFU known_hosts private modes are only guaranteed on first creation, not repaired for existing files/directories

- Files:
  - `packages/core/src/sftp-known-hosts.ts:73`
  - `packages/core/src/sftp-known-hosts.ts:75`
  - `packages/core/src/sftp-known-hosts.ts:78`
  - `packages/core/src/sftp-known-hosts.spec.ts:50`
  - `packages/core/src/sftp-known-hosts.spec.ts:68`
  - `packages/core/src/sftp-known-hosts.spec.ts:70`
- Evidence:
  - `verifyHostKey()` creates the parent directory with `mode: 0o700` and appends the file with `mode: 0o600` at `packages/core/src/sftp-known-hosts.ts:73` through `packages/core/src/sftp-known-hosts.ts:78`.
  - Node's `mkdir(..., { mode })` and `appendFile(..., { mode })` only establish modes when creating new filesystem entries. They do not tighten an existing `~/.aiftp` directory or existing `known_hosts` file.
  - The test asserts first-creation modes at `packages/core/src/sftp-known-hosts.spec.ts:50` and `packages/core/src/sftp-known-hosts.spec.ts:68` through `packages/core/src/sftp-known-hosts.spec.ts:70`, but there is no test for pre-existing permissive modes.
- Impact:
  - Fingerprints are public-key material, not credentials, so this is a hardening issue rather than a secret leak.
  - On machines upgraded from older versions or manually created state, the code can leave `known_hosts` more readable/writable than intended, contrary to the Task 13 requirement that the file be `0600` and parent directory `0700`.
- Reproduction:
  - Pre-create `~/.aiftp` as `0755` or `known_hosts` as `0644`.
  - Run an SFTP first pin.
  - The append succeeds, but the existing mode is not repaired by the code path above.
- Recommended fix:
  - After `mkdir`, explicitly `chmod(dirname(knownHostsPath), 0o700)` on POSIX.
  - Open or write the known_hosts file in a way that allows an explicit `chmod(knownHostsPath, 0o600)` after creation/update.
  - Add a regression test with pre-existing permissive directory/file modes.

### MEDIUM-1 (`remote_root` in MCP payloads) → ACCEPTED as an intentional exception (not a vulnerability)

- **Decision**: `remote_root` remains in MCP `destination` / `expected_remote_root` / prepare payloads. No code change. Security gate: **GO**.
- **Rationale**:
  1. **Pre-existing, not a v0.12 regression** — `git show main:packages/mcp/src/index.ts` already exposes `remote_root` / `expected_remote_root` in 19 places (e.g. `expected_remote_root: profile.remote_root` at the push-prepare handler; top-level `remote_root` in status/rollback). F3 surfaced the same value in a new `destination` block; it introduced no new field to the wire.
  2. **Zero secrecy benefit** — `remote_root` is a plaintext field in `.aiftp.toml`, which lives in the MCP server's working directory. The MCP client (the operator's own AI agent, operating in that project) can already read the file directly. Redacting it from the response hides nothing.
  3. **Not a credential** — the redaction contract exists to keep **credentials** off the wire (those live in the OS Keychain). `remote_root` is deploy metadata the AI legitimately needs to verify the destination at the confirm step; removing it degrades the prepare→confirm safety UX for no gain.
  4. The forbidden-field list that produced this finding (supplied in the review brief) over-specified by including `remote_root`. The correct contract is credentials-only.
- **Authoritative redaction contract (credentials-only)** — MCP responses MUST NOT expose: `host`, `user`, `port`, `password`, `keychain_service`, `account`, `ssh_key_path`. MCP responses MAY expose deploy metadata: `remote_root`, `local_root`, `protocol`, `server_kind`, `profile`, `site`, `label`, `diff_hash`. `DestinationSummary` / `SiteSummary` are validated against the credentials-only list (still explicit-mapping / no-spread).
- **Rejected alternative**: strip `remote_root` from MCP (reviewer's strict fix) — rejected because it provides no real secrecy (see 2), breaks the confirm-time destination check, and is a breaking change to the v0.11 wire format.
- **Revisit condition**: if a future requirement treats `remote_root` as tenant/domain-identifying sensitive data, reintroduce as a finding.

### LOW-1 (registry name/path validation) → DEFERRED to v0.12.1 backlog

Legitimate hardening. Non-blocking for v0.12: exploiting the `init --from` shadowing requires hand-editing `~/.aiftp/sites.toml`, i.e. an actor who already has local filesystem access; and F2 does not inherit credentials regardless. Tracked for v0.12.1 (add a `^[A-Za-z0-9._-]+$` site-name allowlist, normalize/require absolute `path` on read, tests for `../prod` / `client/a` / `gw:co` / control chars).

### LOW-2 (known_hosts perms not repaired for pre-existing files) → DEFERRED to v0.12.1 backlog

Legitimate hardening. Non-blocking: fingerprints are public-key material, not secrets, and fresh installs get `0o700` dir / `0o600` file correctly. Tracked for v0.12.1 (explicit `chmod` of dir/file after mkdir/append on POSIX + regression test with pre-existing permissive modes).

### Net disposition

No CRITICAL/HIGH. MEDIUM-1 resolved as documented intentional exception. Two LOW hardening items deferred to v0.12.1. **v0.12 security gate: GO.** Release remains 田中さん's decision at Task 15.

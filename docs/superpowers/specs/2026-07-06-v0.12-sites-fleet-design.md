# v0.12 Direction Design — サイト台帳（fleet）: 多サイト運用者のための管理レイヤー

- **日付**: 2026-07-06
- **状態**: **Approved**（2026-07-06 田中さん承認・Open Questions 決定済み → implementation plan 起案へ）
- **起点**: 本人ドッグフード（glocalworks.co.jp を Codex / Claude 経由で本番運用）で判明した実運用痛点
- **前提 spec**: `2026-05-25-v0.11-direction-design.md`（v0.11 凍結内容）

## 1. 背景 — なぜ v0.12 は「多サイト」なのか

### 1.1 ドッグフードで出た3痛点（2026-07-06 ヒアリング）

| # | 痛点 | 根本原因 |
|---|---|---|
| P1 | サイトごとの初期設定が手間 | サイト追加のたびに init を最初から繰り返す。既存サイトの設定知識（safety/backup/接続チューニング等）を再利用する仕組みが無い |
| P2 | どのサイトに上がるか不安 | フォルダ⇔サイトの対応が運用者の頭の中にしか無い。confirm ゲートはファイル一覧を見せるが「どこに」上がるかの宣言が弱い |
| P3 | 資格情報の管理が煩雑 | サイトが増えると Keychain エントリが増えるが、一覧・突合する手段が無い。さらに init デフォルトの service 名 `aiftp:<profile>` は**サイト間で衝突しうる**（後述 §3.4） |

### 1.2 事業との整合

「複数サイトを1事業者が預かって AI で更新する」= 更新代行ビジネス（ルート D）の運用基盤そのもの。作者本人が最初の代行事業者であり、この機能群は自社サービスの原価を直接下げる。git-ftp / FFFTP / 大手 AI ツールのいずれも「多数サイトを預かる事業者の安全レイヤー」には向かっておらず、差別化軸になる。

### 1.3 現状実装の事実（2026-07-06 調査）

- 設定は**プロジェクトローカル** `.aiftp.toml`（schema v2、`[profile.X]` × N）。ホームディレクトリにグローバル状態は持たない
- `aiftp auth list` / MCP `aiftp_profile_list` は**単一ファイル内**のプロファイル一覧のみ。**複数プロジェクト横断の一覧機能は存在しない**
- FileZilla import（`aiftp import filezilla <path>`）は複数 `<Server>` の一括取り込みに対応済み（prepare→confirm 2段階）
- Keychain: service = `[profile.X].keychain_service`（init デフォルト `aiftp:<profile>`）、account = `user`
- state / backups / logs はすべて `<project>/.aiftp/` 配下に profile 別で分離

## 2. ゴールと非目標

### ゴール

1. **G1（P3, P2 対応）**: 運用者が「いま何を預かっていて、どれが健全か」を1コマンド／1 MCP ツールで見られる
2. **G2（P1 対応）**: 2サイト目以降のセットアップを「差分だけ答える」作業に短縮する
3. **G3（P2 対応）**: デプロイの宛先を構造的に宣言・照合し、「取り違えの恐怖」を仕組みで潰す
4. **G4（P3 対応）**: Keychain service 名のサイト間衝突をデフォルトで起こさない

### 非目標（変更しない既存方針）

- GUI / デスクトップアプリ化はしない（AI-invisible 検証完了までの凍結を維持）
- watch モード・Hook 自動 push は対象外（従来どおり）
- Pro 機能化・課金はしない（ADR 0001 据え置き）
- 暗号化 default ON / hard-exclude / Keychain-only / prepare→confirm 2段ゲートは**一切緩めない**
- `.aiftp.toml` schema v2 の破壊的変更はしない（本 spec はすべて追加的）

## 3. 設計

### 3.1 F1: サイト台帳 — `aiftp sites`（G1）

**グローバル台帳ファイル** `~/.aiftp/sites.toml`（Windows: `%USERPROFILE%\.aiftp\sites.toml`）を新設する。

```toml
schema_version = 1

[sites.gwco]
path = "/Users/alice/Projects/Web/ExampleCorp"   # プロジェクトルート（.aiftp.toml の場所）
label = "example-corp.co.jp"                      # 人間が読むサイト表示名
default_profile = "production"                    # 省略時は当該プロジェクトの default profile
```

**設計原則: 台帳はポインタのみ。secret も接続情報も持たない。**
- host / user / password / remote_root は台帳に**書かない**。一覧表示時に各プロジェクトの `.aiftp.toml` + Keychain 照会をライブで解決する（single source of truth の維持、スケール時の陳腐化・秘匿情報散在の防止）
- Local-first 原則はそのまま：台帳もローカルファイルのみ、クラウド同期なし

**CLI**:

```
aiftp sites                 # 一覧: name / label / profile / protocol / credential status / last push / path 健在性
aiftp sites add [path]      # カレント（または指定）プロジェクトを台帳に登録
aiftp sites remove <name>   # 台帳から除去（プロジェクト自体には触れない）
aiftp sites doctor          # 全サイトに profile_test（接続サブセット診断）を順に実行
```

一覧の each 行はプロジェクトの `.aiftp.toml`（プロファイル定義）、`.aiftp/log.jsonl`（最終 push 日時）、Keychain（credential presence のみ）から合成する。パスが消えている／`.aiftp.toml` が無いサイトは `missing` と表示し、エラーで落とさない。

**init との統合**: `aiftp init` 完走時に「Register this site in the global registry? (Y/n)」を追加（デフォルト Yes）。サイト名は label から自動提案。

**MCP**: 読み取り専用 `aiftp_sites_list` を追加。返却は REDACTED 方針を `aiftp_profile_list` に揃える：
- 返す: site name / label / path / profile 名 / protocol / credentialsStatus / lastPushAt
- 返さない: host / user / remote_root / keychain_service

### 3.2 F2: 設定継承 — `aiftp init --from`（G2）

```
aiftp init --from <site-name | path>
```

- 継承元（台帳のサイト名 or 直接パス）の `.aiftp.toml` から **[safety] [backup] [connection] [encoding] [quirks] [walk] [preflight] [exclude]** の全セクションと `server_kind` / `protocol` / `port` / `ftps_mode` / `passive_mode` をプリロード
- 質問するのは**差分のみ**: profile 名 / host / user / remote_root / local_root / password / consent（11 フィールド → 実質 7 フィールドに短縮。テンプレート選択もスキップ）
- `--template` と `--from` の併用はエラー（挙動が曖昧になるため）。`--from` は「実在サイトの運用実績ごと引き継ぐ」、`--template` は「業種プリセットから始める」と役割を分ける
- FileZilla 一括 import は既存機能をそのまま案内（本 spec ではドキュメント整備のみ）

### 3.3 F3: 宛先宣言 — deploy destination declaration（G3）

**CLI**: push / rollback の confirm プロンプト冒頭に宛先バナーを必ず表示する。

```
⛳ 宛先: gwco (example-corp.co.jp)
   ftps://production → /public_html   [server: starserver]
   local: /Users/alice/Projects/Web/ExampleCorp
```

ファイル一覧より**前**に出す。`--yes` 系の省略フラグでもバナーは省略しない。

**MCP**:
- `aiftp_push_prepare` / `aiftp_rollback_prepare` の応答に `destination` ブロック（site name / label / profile / remote_root / server_kind。host は含めない）を追加。AI はこれをユーザーへの確認文に使う
- `aiftp_push_prepare` に**任意パラメータ `expected_site`** を追加：指定された場合、台帳上の site name / label と照合し、不一致なら **prepare 自体を拒否**（`site-mismatch` エラー）。tool description で「常に指定すること」を AI に推奨
- confirm は従来どおり plan_id / diff_hash / TTL に束縛（変更なし）

### 3.4 F4: Keychain service 命名のサイト衝突解消（G4）

**問題**: init デフォルトの `keychain_service = "aiftp:<profile>"` は、複数プロジェクトが同名プロファイル（例: production）を使うと**同一 service に別サイトの認証情報が衝突**する（account = user が同じ場合、後勝ちで上書き・取り違えのリスク）。

**変更**: init（および `init --from`）のデフォルト提案を `aiftp:<site-name>-<profile>`（例: `aiftp:gwco-production`）に変更する。site-name は台帳登録名（未登録時はディレクトリ名から提案）。

- 既存の `.aiftp.toml` は `keychain_service` を明示保持しているため**影響なし**（migration 不要）
- `aiftp doctor` に「service 名がサイト非固有（`aiftp:<profile>` 形式）で、台帳に同名 profile が複数ある」場合の warn を追加

## 4. セキュリティ不変条件（本 spec で変わらないこと・強化されること）

| 項目 | 扱い |
|---|---|
| 台帳ファイルの内容 | ポインタ（path/label/profile 名）のみ。host・user・secret は不保持 |
| MCP `aiftp_sites_list` | REDACTED（`aiftp_profile_list` と同方針） |
| prepare→confirm 2段ゲート | 変更なし。F3 は表示・照合の**追加**であり緩和ではない |
| 暗号化 default ON / hard-exclude / パスワード CLI 引数禁止 / ログマスキング | 変更なし |
| `expected_site` 照合 | fail-closed（不一致は拒否。台帳未登録サイトで指定された場合も拒否） |
| 台帳の書き込み | `sites add/remove` と init 末尾の確認プロンプトのみ。MCP からの台帳書き込みツールは**提供しない**（v0.12 では読み取り専用） |

## 6. 検証計画

1. **TDD**: 既存基準を維持（vitest、カバレッジ 80%+、baseline 767 passed から加算）
2. **Codex クロスレビュー**: 実装後に独立レビュー（従来の 3 ラウンド体制。特に F4 の Keychain 変更と F3 の fail-closed 照合はセキュリティ観点必須）
3. **再ドッグフード**: 田中さん自身が **2サイト以上**（glocalworks.co.jp + もう1サイト）で以下を確認
   - `aiftp sites` で全サイトの健全性が1画面で見えるか（P3 解消）
   - `init --from` で2サイト目の追加が体感で「差分だけ」になったか（P1 解消）
   - AI 経由 push で宛先バナー／`expected_site` が取り違え不安を消したか（P2 解消）
4. **リリース判定**: v0.11 と同じ 100 点ルーブリック方式（90+ で GO）

## 7. 実装タスクの粗い分解（plan 起案時に精緻化）

1. core: sites registry module（read/write `~/.aiftp/sites.toml`、path 解決、live 合成）
2. cli: `aiftp sites` / `sites add` / `sites remove` / `sites doctor`
3. cli: init 末尾の台帳登録プロンプト + keychain_service デフォルト変更（F4）
4. cli: `init --from`（継承ロード + 差分質問フロー）
5. core+cli: 宛先バナー（push / rollback confirm）
6. mcp: `aiftp_sites_list`（read-only, REDACTED）
7. mcp: prepare 応答への `destination` ブロック + `expected_site` fail-closed 照合
8. core: doctor への keychain 衝突 warn
9. （併載時）SFTP host key TOFU: `.aiftp/known_hosts` + doctor check
10. docs: README / mcp.md / migration ガイド（※ mcp.md の既知バグ「`npx -y aiftp mcp`→正しくは `@aiftp-tools/cli`」もここで修正）
11. test: 統合テスト（多サイト fixture）+ E2E mock
12. CHANGELOG / version bump 0.11.0 → 0.12.0

## 8. ロードマップ上の位置づけ（2026-07-06 決定）

v0.12 の次は **v0.13 = Claude Desktop 拡張（ワンクリック導入パッケージ）** を最優先候補とする。

- 理由: 教育・研修（受講者が自分の PC で aiftp を使い、講座内で本番公開まで完了する形式）では、受講者 PC のセットアップ摩擦（Node.js 導入 + JSON 手編集）が成立条件レベルのボトルネックになるため
- v0.12 のサイト台帳（グローバル `~/.aiftp/sites.toml`）は、プロジェクトフォルダ文脈を持たない Claude Desktop がサイトを解決するための前提部品でもある（v0.12 → v0.13 の依存関係）
- フル GUI（Tauri/Electron）路線の凍結は継続（AI-invisible 検証完了まで着手しない）

## 9. Open Questions — 決定済み（2026-07-06 田中さん回答）

2. **`sites doctor` の既定**: 接続なし（設定整合チェックのみ）。実接続診断は `--connect` オプトイン

   - WP 4 テンプレの `debug.log` 共通 exclude

## 1. 目的と背景

v0.13 は **Claude Desktop 用の `.mcpb`（MCP Bundle）パッケージ**を提供する。

研修商品「コストを抑えた Web サイト作成」の成立条件は、受講者 PC のセットアップ摩擦の除去である。現状、aiftp を使うには **Node.js の導入**と **MCP 設定 JSON の手編集**が必要で、これが研修のボトルネックになる（`training-product-v0.1.md` §5）。

`.mcpb` はこの2つを構造的に解消する。

| 課題 | `.mcpb` による解消 |
|---|---|
| Node.js の導入 | **Claude for macOS / Windows に Node が同梱**されるため不要 |
| MCP 設定 JSON の手編集 | `manifest.json` の `user_config` から **設定 UI が自動生成**される |
| プロジェクトフォルダの指定 | `directory` 型の**フォルダピッカー**で選択（手打ちゼロ） |
| 認証情報の平文保存 | `sensitive: true` の値は **OS キーチェーン**に格納される |

### 1.1 フル GUI（Tauri/Electron）との関係

フル GUI 路線は凍結を継続する。v0.13 は **GUI を作らずに GUI の目的（セットアップ摩擦の除去）を果たす**選択である。

| | フル GUI（凍結中） | v0.13 `.mcpb` |
|---|---|---|
| UI を誰が作るか | 自分（維持コストが恒久発生） | Claude Desktop が生成 |
| OS 別ビルド・署名・公証 | 必要 | 不要（1つの `.mcpb` が両 OS 共通） |
| AI から見えるか | 見えない | **全操作が MCP ツール経由＝AI-visible** |

**凍結理由（記録の集約）**:

1. **維持コストが一人チームに対して過大** — `docs/roadmap.md`「GUI wrapper in the Free CLI today — maintenance cost is too high for a one-person team at the moment」
2. **Pro 候補であり、需要実証前に有償機能を作らない** — `docs/roadmap.md` Pro 候補表「Maintenance cost is high; Pro can fund it」＋ ADR 0001「Pro 製品は据え置き」
3. **楔ペルソナの確定で想定顧客が射程外になった** — `docs/spec.md` §Phase 5+ の GUI 提案は「非開発者・代理店向け」だが、ADR 0001 で楔を制作者（半技術者）に絞り、v1.0 ゴールから「真の非エンジニアが自力で使える」を外した
4. **AI-first 思想との不整合** — 「MCP サーバが第一級市民、CLI は副産物」（CLAUDE.md）に対し、GUI は AI から不可視な操作面を増やす

**「AI-invisible 検証」の定義（本文書で確定）**: 「AI から不可視な操作面（GUI）に、AI 可視な操作面（MCP/CLI）を超える価値があるか」の検証を指す。解凍の条件は次の2つを**同時に**満たすこと — ①`.mcpb` を配布してなお「GUI でなければ解決しない」摩擦が実利用者から報告されること ②その報告が、有償化を正当化できる規模の持続利用（リリース日スパイクと CI ノイズを除いた継続 DL）に裏打ちされること。

### 1.2 収益方針との関係（2026-07-30 確認）

- **v0.13 の `.mcpb` は MIT 無料**。研修における「無料の教材＝差別化装置」という位置づけを維持する（ADR 0001 と整合、改訂不要）
- **有償ダウンロード販売の候補は将来の GUI 版**であり、これは roadmap の Pro 候補表に元から記載がある
- **Free 側に拡張シーム（プラグイン機構）は仕込まない**（ADR 0001「出す日が来たら 2.0（破壊的変更）で対応」）。有償の余地は「別プロダクト・別 identity」で確保する（§6.4）

## 2. スコープ

### 2.1 やること

- 受講者が **ターミナルを一切開かずに**、導入 → サイト登録 → 接続確認 → テスト push → 本番反映 → ロールバックまで到達できる
- 対象サイトは **1サイト**（`user_config` で1件をブートストラップし、以後は既存の台帳が真実になる）
- **macOS / Windows を同等に対応**（実機検証を両 OS で完了条件とする）

- 多サイトの CRUD（追加・削除・切替）をチャットから行う機能
- `packages/mcp/src/index.ts`（2519行）の分割 — 別 backlog
- Connectors Directory への申請 — 公式ドキュメントは「ディレクトリ掲載はリモート connector 推奨、MCPB は副系統」としており、研修配布に不要
- `.mcpb` の署名 — §6.2 参照
- フル GUI — §1.1 参照

## 3. アーキテクチャ

### 3.1 中核課題: cwd（プロジェクトフォルダ）の不在

現行の MCP サーバは **cwd 中心**の設計である。

- `SiteEntry` は `{ name, path, label?, default_profile? }`（`packages/core/src/sites/types.ts`）で、**プロジェクトフォルダへのポインタ**にすぎない
- host / protocol / remote_root は「そのフォルダの `.aiftp.toml`」から、パスワードは Keychain から解決される
- `resolveDestination`（`packages/mcp/src/index.ts`）は `resolve(entry.path) === resolve(app.cwd)` で宛先を照合する

Claude Desktop はプロジェクトフォルダの概念を持たないため、この前提が成立しない。

### 3.2 解法: 受講者のサイトフォルダを本物のプロジェクトフォルダに仕立てる

Desktop 用の別系統を作らず、**既存の cwd 中心設計をそのまま満たす**。これにより CLI との互換が自動的に保たれる。

起動時のブートストラップ（**冪等**）:

1. `user_config` の `local_root`（フォルダピッカーで選択された受講者のサイトフォルダ）をプロジェクトルートとみなす
2. そこに `.aiftp.toml` を生成する（既存 `init` のテンプレート生成ロジックを再利用）
3. パスワードを **aiftp 自身の Keychain**（`aiftp:<site>-<profile>`）へ書き込む
4. `~/.aiftp/sites.toml` に `{ name, path: local_root }` を登録する
5. MCP サーバの `cwd` を `local_root` に設定する（`createMcpApp({ cwd })`）

以後は**既存の全ツールが無改変で動作する**。

### 3.3 モジュール配置

| 場所 | 責務 |
|---|---|
| `packages/core/src/bootstrap/`（新規） | 冪等ブートストラップの純粋ロジック。fs・Keychain・台帳を注入可能にして単体テスト可能にする |
| `packages/mcp/src/desktop/`（新規） | 起動時のブートストラップ呼び出し、`aiftp_setup` prompt、`aiftp_setup_status` ツール |
| `packages/desktop-ext/`（新規・private / npm 非公開） | `manifest.json` テンプレート、アイコン、バンドルビルド、`mcpb pack` |

> **既存ファイルの扱い**: `packages/mcp/src/index.ts` は既に 2519 行あり、規約上限（800 行）を大きく超えている。ここに Desktop 用コードを足すと悪化するため、**新規コードは上記の別モジュールに置き、`index.ts` への変更は配線 1〜2 行と `push_confirm` の引数追加のみに留める**。`index.ts` 自体の分割は本スコープ外とし、別 backlog に起票する。

## 4. 認証情報とセキュリティ境界

### 4.1 `user_config`

| フィールド | 型 | sensitive | 用途 |
|---|---|---|---|
| `site_name` | string | — | 台帳の識別子。`^[A-Za-z0-9._-]+$`（v0.12.4 で導入した許可リストを流用） |
| `local_root` | directory | — | 受講者のサイトフォルダ（フォルダピッカー） |
| `host` | string | — | 例: `ftp.example.test` |
| `protocol` | string | — | `ftps` / `sftp` / `ftp`。既定 `ftps`。**MCPB の `user_config` は enum 型を持たない**ため、`description` に許容値を明記し、**ブートストラップ側で検証**して不正値は `hint` 付きエラーにする |
| `username` | string | — | FTP ユーザ名 |
| `password` | string | **✅** | OS キーチェーン格納 → env で1回だけ渡る |
| `confirm_phrase` | string | **✅** | 本番反映の合言葉。**ツール出力に一切返さない** |
| `remote_root` | string | — | 例: `/public_html` |

### 4.2 パスワードの通り道（初回限り）

Claude Desktop が `sensitive` 値を OS キーチェーンから復号して env へ注入する → ブートストラップが **aiftp 自身の Keychain へ書き写し、以後 env を読まない**。既に Keychain に保存済みなら env を無視し、ツール応答で「設定画面のパスワード欄は空にしてかまいません」と案内する。

**パスワードが CLI 引数に乗る経路は作らない**（プロジェクト非交渉ルールを維持）。

### 4.3 本番ガード（合言葉方式）

MCP の elicitation（サーバが人間へ直接入力を求める仕組み）は **Claude Desktop では未実装**である（Claude Code v2.1.76 で実装されたが Desktop には未到達）。加えて MCP 仕様は form mode でのパスワード等の要求を禁じている。したがって「人間にしか作れない入力」を成立させる手段は、**モデルが知り得ない共有秘密**に限られる。

1. `push_prepare` が本番プロファイルを検出したとき、**チャレンジコード**（ランダム6文字、プランごとに毎回変わる）と人間向け指示文を返す
2. `push_confirm` は `confirmation: "<チャレンジ> <合言葉>"` の完全一致を要求する。照合は**タイミング安全比較**、保存は**ハッシュ**
3. 合言葉は `user_config` の値であり**ツール出力に一切出さない**ため、モデルは事前に知り得ない → **人間がチャットに打つまで confirm は通らない**

#### 既知の限界（明示する）

人間が一度チャットに合言葉を打つと、その会話の文脈にモデルから見える形で残る。**同一会話内の2回目以降は、モデルが自力で `<新チャレンジ> <合言葉>` を組み立てられる。** 完全な防止には elicitation が必要だが Desktop 未実装のため、v0.13 では次の緩和策を採る:

- 合言葉は **FTP パスワードとは別の文字列**にする（研修で明言し、手順書にも記載）
- `aiftp log` に「合言葉が提示された」事実を毎回記録し、事後追跡可能にする
- Claude Desktop のツール承認ダイアログを二重ゲートとして残す

この限界は `docs/desktop-extension.md` にも記載する。aiftp の信用の土台は安全性であり、限界を隠すと土台が崩れる（ADR 0002 の「誇大広告にしない」方針と同じ）。

### 4.4 既存の安全装置

以下は**素通しで効く**。変更しない。

- **hard exclude**（`wp-config.php` / `.env*` / `db.php`）— 研修の売りそのもの
- **暗号化バックアップ + rollback** — 実習の「戻せる体験」に使う
- **ログのマスキング** — redaction 対象に `confirm_phrase` を追加する（既存契約「認証情報のみ・`remote_root` は許可」を踏襲）
- **`.gitignore` への `.aiftp/` 追加強制** — ブートストラップも既存 `init` と同じ処理を通す。git リポジトリでないフォルダ（受講者は大半こちら）ではスキップする

## 5. オンボーディング体験

### 5.1 設計原則: 起動は必ず成功させる

設定不足（`local_root` 未選択、パスワード未入力）でサーバ起動を失敗させると、Claude Desktop は「接続エラー」としか表示せず、受講者にも講師にも原因が見えない。

**起動は常に成功させ、不足はツール応答で人間語で返す。** 本拡張で最も重要な運用上の設計判断である。

### 5.2 追加する MCP 面（3つ）

**1. `aiftp_setup` prompt** — 導入直後の入口。研修カリキュラム（`training-product-v0.1.md` §4 の午後1・午後2）と1対1で対応する。

| ステップ | 使うツール | 研修での位置づけ |
|---|---|---|
| ① 接続確認 | `aiftp_setup_status` → `aiftp_profile_test` | 午後1「セットアップ」 |
| ② テスト領域へ push | `aiftp_push_prepare` / `_confirm` | 午後2 前半 |
| ③ 本番反映 | 同上（合言葉ゲート） | 午後2 クライマックス |
| ④ 戻す体験 | `aiftp_backup_list` → `aiftp_rollback_prepare` / `_confirm` | 締め |

**2. `aiftp_setup_status` ツール**（新規・読み取り専用） — 判定項目: `user_config` の各欄が埋まっているか / `local_root` が実在するか / `.aiftp.toml` が生成済みか / Keychain にパスワードが保存済みか / 台帳に登録済みか / 合言葉が設定済みか。

**3. `push_confirm` への `confirmation` 引数追加** — 本番プロファイル時のみ必須。他の既存ツールは無改変。

### 5.3 エラー文言

機械可読なエラー識別子は**英語のまま維持**する（`site-mismatch:` 等は既存テストと後方互換の契約）。そのうえで応答に **`hint` フィールドを追加して日本語の対処法を併記**する。

```
error: "bootstrap-incomplete: password not stored"
hint:  "Claude Desktop の設定 → 拡張機能 → aiftp で「パスワード」欄を入力し、Claude Desktop を再起動してください。"
```

受講者は AI 経由で日本語の指示を受け取り、講師は英語識別子でログを追える。

## 6. 配布パッケージ

### 6.1 構成とビルド

```
packages/desktop-ext/
├── manifest.json        # テンプレート（version はビルド時に注入）
├── icon.png             # 512x512 PNG
├── scripts/build.mjs    # server/ 組み立て → manifest 生成 → mcpb pack
└── dist/aiftp-<ver>.mcpb
```

`manifest.json` の要点:

```json
{
  "manifest_version": "0.3",
  "name": "aiftp",
  "display_name": "aiftp — FTP/FTPS 安全デプロイ",
  "version": "0.13.0",
  "server": {
    "type": "node",
    "entry_point": "server/index.js",
    "mcp_config": {
      "command": "node",
      "args": ["${__dirname}/server/index.js"],
      "env": {
        "AIFTP_PROJECT_DIR": "${user_config.local_root}",
        "AIFTP_BOOTSTRAP_SITE": "${user_config.site_name}",
        "AIFTP_BOOTSTRAP_PASSWORD": "${user_config.password}",
        "AIFTP_CONFIRM_PHRASE": "${user_config.confirm_phrase}"
      }
    }
  },
  "compatibility": {
    "platforms": ["darwin", "win32"],
    "runtimes": { "node": ">=22.0.0" }
  }
}
```

`AIFTP_PROJECT_DIR` が §3.1 の cwd 問題の解になる。

**依存の同梱方法 — バンドラは使わない。** esbuild で単一ファイルに固めず、`pnpm deploy --prod` で実体の `node_modules` を `server/` に配置する。理由: `ssh2`（SFTP 用）は動的 require とオプショナルなネイティブ依存 `cpu-features` を持ち、バンドラで壊れやすい既知の地雷であるため。研修では「動かない」が最悪の失敗なので堅牢性を優先する。`cpu-features` は optional なので除外し、ピュア JS 暗号にフォールバックさせる → **1つの `.mcpb` が macOS / Windows 共通**で動く。

### 6.2 署名

**v0.13 は未署名で配布する。**

`mcpb sign` の自己署名では「検証済み発行者」扱いにならず警告表示は残る想定（公式ドキュメントに明記がないため、Task 0 で実機確認する）。正式な証明書には費用と手続きが発生し、**無料配布のために取得するのは ADR 0001 の「過剰投資しない」に反する**。

`docs/desktop-extension.md` に警告の意味と安全性の根拠（MIT・ソース公開・ローカル完結・テレメトリなし）を説明する。証明書は将来の GUI 有償版を出すときにまとめて取得する。

### 6.3 バージョン一貫性（必須）

**単一の真実 = monorepo のパッケージバージョン。** 既存の `packages/core/scripts/generate-version.mjs` と同じ仕組みを拡張し、ビルド時に `manifest.json` の `version` をテンプレートから注入生成する（手書きしない）。

同期対象を列挙し、**不一致でビルド／CI が落ちる**ようにする:

- `packages/desktop-ext/manifest.json` の `version`
- `.mcpb` のファイル名（`aiftp-0.13.0.mcpb`）
- `docs/desktop-extension.md` に記載する対応バージョン
- `CHANGELOG.md` の該当セクション
- 研修受講者向け手順書（非公開 `AIftp/docs/` 側）に記載するバージョン

検証はテストで固定する。`manifest.version === pkg.version` かつ「docs 内の記載バージョン === pkg.version」を**実値の突き合わせ**で assert する（「形」で検証しない — v0.12.4 の 1.4% 誤検知の教訓）。

### 6.4 identity の予約（将来の有償 GUI 版との衝突回避）

| 項目 | v0.13 の決定 |
|---|---|
| `manifest.json` の `name` | `aiftp` = Free の MCP バンドルとして確定 |
| 将来の GUI 有償版 | `aiftp-desktop`（仮）を別 identity として予約。名前・設定・キーチェーン項目が衝突しない |
| リポジトリ境界 | GUI は `aiftp-tools/aiftp-pro` 側。Free（MIT）をライブラリとして依存する形にすればライセンス境界が明確 |
| Free 側のフック | **入れない**。今シームを作ると 2.0 で破壊的変更を打つ自由を失う |

### 6.5 リリース

- `.mcpb` は GitHub Release のアセットとして添付する
- CI（release トリガー）で `.mcpb` をビルドし Release へ自動添付する
- 既存の smoke ワークフローに「`.mcpb` の zip 検証 + manifest スキーマ検証」を追加する
- リリース手順（tag → `pnpm publish` ×3 → 実測検証 → Release → smoke green）は `memory.md` の恒久手順に従う。**`npm publish` は使わない**（v0.12.2 事故）

## 7. テストと完了条件

### 7.1 テスト戦略

| 層 | 対象 | 方針 |
|---|---|---|
| 単体 | `core/src/bootstrap/` | 純粋ロジック。**冪等性**（2回実行で同結果・既存 `.aiftp.toml` を壊さない）を検証。**HOME 隔離は `HOME` + `USERPROFILE` を必ず併設**（v0.12 の教訓） |
| 単体 | 合言葉ゲート | チャレンジ不一致・合言葉不一致・両方不一致・未設定を個別に検証。**実値と比較する形で書く** |
| 単体 | バージョン一貫性 | `manifest.version === pkg.version` かつ docs 記載バージョン一致 |
| 統合 | `aiftp_setup_status` | 設定欠落パターンごとに正しい不足項目と `hint` を返すか |
| 統合 | 起動の堅牢性 | 設定が空・`local_root` 不在でも**サーバ起動が成功する**こと |
| パッケージ | `.mcpb` | zip 展開して `server/index.js` が `node` 単体で起動しハンドシェイクが通るか。**`AIFTP_TEST_NO_REAL_KEYCHAIN=1` を効かせ実キーチェーンを spawn しない**（v0.12.4 で導入済みのガード） |

CI マトリクスは既存どおり `[macos, windows] × [22, 24]`（**ubuntu ジョブは存在しない**）。

### 7.2 完了条件（実機検証 — macOS / Windows 両方）

1. `.mcpb` をダブルクリック → 設定 UI 入力 → インストール成功
2. `aiftp_setup` prompt から接続確認が通る
3. **テストサブディレクトリ**への push 成功（**本番 `/public_html` 直下は使わない** — 非交渉ルール）
4. 本番反映が**合言葉なしで拒否され、合言葉ありで通る**
5. rollback で復元一致
6. Keychain にパスワードが保存され、**設定画面のパスワード欄を空にしても動作継続**
7. `wp-config.php` / `.env` を置いても push 対象外（hard exclude の実機確認）

## 9. リスク

| リスク | 影響 | 対応 |
|---|---|---|
| Claude Desktop 同梱 Node が 22 未満 | 設計の前提が崩れる | **Task 0 で最初に実測**。ビルドターゲットを下げるか `runtimes.node` を実態に合わせる |
| 未署名警告が受講者の不安を招く | 研修の進行が止まる | 手順書で警告の意味と安全性の根拠を説明。講師が導入時に触れる |

| `pnpm deploy` の成果物に開発依存が混入 | バンドルサイズ肥大・不要な攻撃面 | ビルド後に `server/node_modules` の内容を検証するテストを置く |
